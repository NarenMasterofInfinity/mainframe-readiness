# Files to results

## Product contract

Given a local selection of application resources on the installed workbench, produce a complete assessment of the supplied material. The operator supplies **one selection and zero metadata fields**. Selecting files in the picker or dropping them starts the run. The equivalent proposed CLI is `assess <folder>`, `assess <archive.zip>` or `assess <file1> <file2> ...`. All three return the run identifier, three results and paths to the two local reports. A result with unresolved planning questions is a successful product outcome.

The team's setup decision covers the workstation and approved runtime once. A new application needs no registration, mainframe connection, credentials, written scope, dependency list, library map, questionnaire, expected-categories sheet, prompt or model. The unit of assessment is the selected export. Multiple workloads can share that perimeter. Production completeness and criticality need evidence of their own. A prioritized collection request helps the reviewer decide what to do next. The hackathon demonstration should measure each job directly. ## From one selection to a saved result

| Stage | What executes automatically | Durable output and decision on uncertainty |
|---|---|---|
| 1. Admit the selection | Allocate a workspace application key and run ID. Enumerate logical paths, check bounds, stage regular bytes read-only and hash. A new assessment always has its own application key. Add evidence inherits the selected parent's key. | Input receipt with counts, origin, hashes and rejection reason when needed. Same filenames across submissions never combine applications. |
| 2. Build the working scope | Use all admitted files. Infer supported file types, source layout and candidate workload from affirmative clues. Index explicit library/qualifier hints without assigning precedence from directory order. | Generated settings and per-field origin. Label business scope “unreviewed.” Multiple entry-point groups remain visible. Unknown owner, dialect, encoding or criticality stays explicit. |
| 3. Discover evidence | Run only the applicable first-party readers on the staged bytes. Extract definitions, uses, data operations, configuration statements and potential document leads with exact physical spans. | Per-artifact status and coverage. For ordinary runbooks, a named subject and nearby heading can locate text for review. A keyword cannot certify a control or a recovery procedure. |
| 4. Resolve and build the map | Match typed names within scope, join a step's DD binding to a program's file operation and trace online transaction/program/map/table paths. Record unresolved and competing targets. | Directed graph, source locators, entry paths, possible handoffs, impacted entries, boundary candidates and caveats. Declared schedule order has its own evidence trail. |
| 5. Evaluate the decision | Apply the same seven-dimension rubric and expected-evidence rules on both applications. Calculate complexity signals, confidence checks and readiness gates independently. | For every material conclusion, record the fact or gap, rule version, evidence class, scope and limit. Rank hotspots and next steps. Candidate planning considerations include what evidence could overturn them. |
| 6. Publish and open | Validate references, serialize a single revision and stage the report pair in the run workspace. Publish the completed snapshot and both files together. Present the overview automatically. | Local HTML and JSON already exist when “Completed” appears. The overview leads with the three answers, the strongest reason for each, the largest unresolved question and its next action. Scope and coverage accompany every export. |
| 7. Investigate or reassess | A user may follow the evidence, review a claim, copy a report, add another resource to this app, or start a separate assessment. Each review references a revision. A child run consumes the base snapshot plus the selected changes. | Compare actual changed observations, checks, gates and actions. Keep parent bytes and machine results. A second independent app uses exactly the same flow. |

## Defaults that prevent accidental claims

| Question a setup wizard might ask | Automatic decision | What would justify changing it |
|---|---|---|
| What is the application called? | Display sanitized folder/archive stem or “Selected files” plus a short run label. Construct a separate opaque application key. | Optional display rename affects presentation. An explicit child relationship establishes continuity across changed files. |
| Which paths belong together? | Directory paths are relative to the selected root. A plain selection uses supplied relative paths where available, otherwise distinct basenames. Refuse indistinguishable path collisions and suggest selecting the enclosing folder. | A reviewer may scope a child assessment to a subset. Preserve excluded paths and reasons. A disconnected component alone does not establish another application. |
| Is it batch or online? | JOB/step evidence supports a batch observation. A transaction binding or supported CICS operation supports an online observation. Both may coexist. | Record supporting IDs and the source of any later declaration. No affirmative clue gives unknown. Absence never establishes an exclusion. |
| Where should lookups search? | Consider definitions of the correct kind across the submitted perimeter. Unique eligible names can resolve within the export. With duplicate names and no evidenced precedence, return the candidates. | An explicit scoped override or reviewed binding can justify precedence. Path order, archive order and filename resemblance have no vote. |
| How do we handle system setup, owners and target platform? | Apply the tool's fixed, versioned rubric. Leave deployment environment, owners, business criticality and target assumptions unknown. Treat discovered entries conservatively for open requirements. | Supplied evidence or an attributed reviewer decision can refine scope. Indicate whether an owner is documented or simply the role requested to investigate. |

## Exceptions and completion

A package-level failure that prevents safe or meaningful admission returns a precise receipt and the smallest practical remedy. An unreadable member, contradictory evidence, missing copybook, ambiguous target or unrecognized document in an admitted selection yields a completed assessment with gaps. If all files are unsupported, return the inventory, unknowns, empty graph with reason, and an actionable request. If report publication fails, retain diagnostics, preserve the last valid snapshot and offer a local retry. The machine must never wait indefinitely for a person to choose a type or press Continue.

On a completed run the user may save another report with selected options. For revision zero the default pair already exists. A reviewed export is pinned to the selected revision. Store pairs under distinct revision directories. Once published, an older pair stays retrievable. For the files-only flow, delivery is verified by the examiner opening both default files with the app closed. Capture the paths and pinned revision as evidence.

## Single acceptance endpoint

Use the same build, rules and clean local workspace. Select Harbor Stock resources. Record the number of mandatory fields, prompts after selection, elapsed time to a complete result and the report paths. Trace a possible stock handoff to both jobs. Select the schedule CSV in **Add evidence** and show exactly which claim changed while recovery remains open. Select Cedar Permits resources as a new assessment and trace the online entry to its table. Examine a boundary crossing, compare the two scopes, then reopen the saved HTML and verify its JSON references offline. Both file-only runs must have **zero** mandatory metadata fields and **zero** blocking questions after an admissible selection. Record failures, timings and evidence from the delivered software.
